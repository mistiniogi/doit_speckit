# Data Model: Goal Reordering

**Phase**: Phase 1 (Design & Contracts)  
**Date**: 2026-02-15  
**Status**: Complete

## Overview

This document defines the data structures and entities needed to support goal reordering via drag-and-drop. The data model extends the existing 001-goal-tracker entities with an `order` property to track position within each column.

## Entity Definitions

### Goal Entity

**Purpose**: Represents a single user goal with reordering capability

**Fields**:

```typescript
interface Goal {
  id: string;                    // UUID, Unique identifier
  title: string;                 // 1-100 chars, non-whitespace, required
  endDate: string;               // ISO 8601 date (YYYY-MM-DD), required
  status: 'active' | 'completed'; // Current state
  completedDate: string | null;  // ISO 8601 timestamp when marked complete
  createdDate: string;           // ISO 8601 timestamp when created
  order: number;                 // NEW: Position within its column (0-based index)
}
```

**Type Constraints**:
- `id`: Must be unique within localStorage
- `title`: Must be trimmed, non-empty
- `endDate`: Must be today or in future (enforced at form level)
- `status`: Enum of exactly two values
- `completedDate`: Only set when status === 'completed'
- `order`: Non-negative integer, unique within each status group

**Validation Rules**:

| Field | Rule | Error Message |
|-------|------|---------------|
| `title` | Length 1-100, no leading/trailing whitespace | "Goal title must be 1-100 characters" |
| `endDate` | Valid ISO date, >= today | "End date must be today or in the future" |
| `status` | Must be 'active' or 'completed' | "Invalid status" |
| `order` | Non-negative integer | "Order must be non-negative" |
| `order` | Unique within status group | "Order conflict within column" |

**State Transitions**:

```
Initial State (new goal):
  status: 'active'
  order: (max order in active goals) + 1
  completedDate: null

Transition 1 - Mark Complete:
  active → completed
  order: (max order in completed goals) + 1
  completedDate: new Date().toISOString()

Transition 2 - Delete:
  active/completed → [removed]
  All subsequent goals in same status: order -= 1

Transition 3 - Reorder (within column):
  order: [new position]
  Other goals in same column: order adjusted (no gaps)
```

### GoalList Entity

**Purpose**: Container managing all goals with ordering logic

**Fields**:

```typescript
interface GoalList {
  goals: Goal[];                    // All goals (active + completed)
  activeGoals: Goal[];              // Filtered: status === 'active', sorted by order
  completedGoals: Goal[];           // Filtered: status === 'completed', sorted by order
}
```

**Computed Properties** (derived, not stored):

| Property | Calculation | Purpose |
|----------|-------------|---------|
| `activeGoals` | Goals where status === 'active', sorted by order asc | Display in left column |
| `completedGoals` | Goals where status === 'completed', sorted by order asc | Display in right column |
| `goalById(id)` | Hash lookup by goal.id | O(1) retrieval |

**Invariants** (must be maintained):

```
1. All goals in activeGoals have order values [0, 1, 2, ..., n] with no gaps
2. All goals in completedGoals have order values [0, 1, 2, ..., m] with no gaps
3. No two goals with same status have same order value
4. order property is always >= 0
5. activeGoals.length === goals.filter(g => g.status === 'active').length
6. completedGoals.length === goals.filter(g => g.status === 'completed').length
```

## Storage Schema

### localStorage Key Structure

```
Key: "doit_goals"
Value: JSON.stringify(goals)

Key: "doit_goal_order_active"
Value: JSON.stringify({ 
  goalId: order,
  goalId: order,
  ...
})

Key: "doit_goal_order_completed"
Value: JSON.stringify({ 
  goalId: order,
  goalId: order,
  ...
})
```

**Rationale**: Order is stored separately for integrity. If localStorage corruption occurs, order can be regenerated by sorting on goal creation date.

### Migration Strategy

**From 001-goal-tracker → 002-goal-reorder**:

When the app detects existing goals without `order` property:
1. Load all goals from localStorage
2. For each status group (active, completed), sort by createdDate ascending
3. Assign order values 0, 1, 2, ... to maintain chronological order
4. Save updated goals with new `order` properties
5. Create order index keys for future sync operations

```typescript
// Migration function
function migrateGoalsToHaveOrder(goals: Goal[]): Goal[] {
  const activeGoals = goals.filter(g => g.status === 'active').sort((a, b) => 
    new Date(a.createdDate).getTime() - new Date(b.createdDate).getTime()
  );
  
  const completedGoals = goals.filter(g => g.status === 'completed').sort((a, b) =>
    new Date(a.createdDate).getTime() - new Date(b.createdDate).getTime()
  );
  
  let allGoals: Goal[] = [];
  
  activeGoals.forEach((goal, index) => {
    allGoals.push({ ...goal, order: index });
  });
  
  completedGoals.forEach((goal, index) => {
    allGoals.push({ ...goal, order: index });
  });
  
  return allGoals;
}
```

## Ordering Logic

### Adding a New Goal

```typescript
function addGoal(goals: Goal[], title: string, endDate: string): Goal {
  const activeGoals = goals.filter(g => g.status === 'active');
  const maxOrder = Math.max(...activeGoals.map(g => g.order), -1);
  
  const newGoal: Goal = {
    id: generateUUID(),
    title: title.trim(),
    endDate,
    status: 'active',
    completedDate: null,
    createdDate: new Date().toISOString(),
    order: maxOrder + 1
  };
  
  return newGoal;
}
```

### Completing a Goal

```typescript
function completeGoal(goals: Goal[], goalId: string): Goal[] {
  const completedGoals = goals
    .filter(g => g.status === 'completed')
    .sort((a, b) => a.order - b.order);
  
  const maxOrder = completedGoals.length > 0 
    ? Math.max(...completedGoals.map(g => g.order))
    : -1;
  
  return goals.map(g => {
    if (g.id === goalId) {
      return {
        ...g,
        status: 'completed',
        completedDate: new Date().toISOString(),
        order: maxOrder + 1
      };
    }
    return g;
  });
}
```

### Reordering Goals (Drag-and-Drop)

```typescript
function reorderGoals(
  goals: Goal[],
  goalId: string,
  newIndex: number,
  status: 'active' | 'completed'
): Goal[] {
  const goalsInStatus = goals.filter(g => g.status === status).sort((a, b) => a.order - b.order);
  
  // Find the moving goal
  const movingGoalIndex = goalsInStatus.findIndex(g => g.id === goalId);
  if (movingGoalIndex === -1) throw new Error('Goal not found');
  
  // Remove from current position
  const reordered = [...goalsInStatus];
  const [movedGoal] = reordered.splice(movingGoalIndex, 1);
  
  // Insert at new position
  reordered.splice(newIndex, 0, movedGoal);
  
  // Reassign order values [0, 1, 2, ...]
  const updatedInStatus = reordered.map((g, idx) => ({ ...g, order: idx }));
  
  // Merge back with other status group
  const otherStatus = status === 'active' ? 'completed' : 'active';
  const unchanged = goals.filter(g => g.status === otherStatus);
  
  return [...updatedInStatus, ...unchanged];
}
```

### Deleting a Goal

```typescript
function deleteGoal(goals: Goal[], goalId: string): Goal[] {
  const goalToDelete = goals.find(g => g.id === goalId);
  if (!goalToDelete) throw new Error('Goal not found');
  
  const status = goalToDelete.status;
  
  // Remove the goal
  const remaining = goals.filter(g => g.id !== goalId);
  
  // Reorder remaining goals in same status to fill the gap [0, 1, 2, ...]
  const goalsInStatus = remaining
    .filter(g => g.status === status)
    .sort((a, b) => a.order - b.order);
  
  const reordered = goalsInStatus.map((g, idx) => ({ ...g, order: idx }));
  const unchanged = remaining.filter(g => g.status !== status);
  
  return [...reordered, ...unchanged];
}
```

## Data Flow Diagram

```
User Action: Drag Goal X from position 0 to position 2
                    ↓
        Sortable.js captures event
                    ↓
        Call reorderGoals(goals, 'goal-x-id', 2, 'active')
                    ↓
        Recalculate order: [0, 1, 2, ...] for active goals
                    ↓
        Update React state: setGoals(updated)
                    ↓
        Save to localStorage: goals + order index
                    ↓
        Trigger storage event (cross-tab sync)
                    ↓
        Other tabs: Detect storage event → update state
                    ↓
        UI re-renders in all tabs with new order
```

## Edge Cases & Handling

| Scenario | Handling |
|----------|----------|
| Goal deleted during drag | Sortable.js `cancel()` method to abort drag |
| Goal marked complete during drag | same as above - abort drag |
| Rapid reordering in multiple clicks | Queue updates to localStorage; localStorage is atomic |
| localStorage full | UI should show error; allow deletion of goals |
| Corrupted order property | On app start, validate and regenerate from goal IDs |
| Offline/no localStorage | Goals in memory only; refresh loses data (acceptable for MVP) |

## Performance Considerations

| Operation | Complexity | Optimization |
|-----------|-----------|---------------|
| Add goal | O(n) to find max order | Maintain running max order |
| Complete goal | O(n) | Maintain running max order per status |
| Reorder goal | O(n) to reassign orders | Necessary; n is typically <50 |
| Delete goal | O(n) to shift orders | Necessary; n is typically <50 |
| Render goals | O(n) for mapping | React reconciliation handles efficiently |

**For MVP scale (10-50 goals)**: All operations are negligible in performance impact.

## Backward Compatibility

When 002-goal-reorder is deployed alongside 001-goal-tracker:

1. Existing goals load without `order` property
2. Migration function automatically assigns order values
3. New goals created after deployment include `order`
4. Old UI (without reordering) still works; order property is ignored

**No database migration required** (localStorage only).

## Conclusion

The data model extends Goal and GoalList with an `order` property and supporting logic. This enables within-column reordering while maintaining data integrity and supporting cross-tab synchronization. All modifications are backward-compatible with existing goal data.
